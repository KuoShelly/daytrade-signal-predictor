# 當沖熱門股預測（Day-Trade Signal Predictor）

用台股日內技術指標、收盤排行、均線、融資券、當沖成交量等多來源資料，
預測「明天當沖成交比重會偏高的股票」，協助交易員縮小每日盯盤範圍。

> **關於資料來源**：原始版本串接的是內部行情平台的私有 SDK（含連線資訊），
> 這份公開版本把資料存取抽成 `MarketDataSource` 抽象介面，並提供
> `MockMarketDataSource` 產生欄位結構相同的示範資料，讓任何人都能
> `clone` 下來直接跑通整條 pipeline、驗證程式邏輯本身的正確性。
> 讀「三、工程設計決策」第 1 點了解為什麼要這樣拆。

---

## 一、業務問題

台股當沖交易熱度集中在少數股票，但每天上千檔標的，人工篩選「今天當沖熱度會偏高」
的股票非常耗時，且容易漏掉盤中訊號還沒明顯發酵、但技術面已經出現徵兆的股票。

**目標**：用前一交易日（以及更早）的技術指標與籌碼面資料，預測「今天當沖比例會排進
全市場前 30 名」的股票名單，讓交易員可以優先關注這份清單，而不是逐一掃過整個市場。

**Label 定義**（`src/labeling.py`）：
- 當日成交量 > 10,000 股（避免流動性太差的股票干擾）
- 在符合條件的股票中，依「當沖成交量 / 總成交量」排序，取每天前 30 檔為正樣本

## 二、Pipeline 架構

```
MarketDataSource（5 張來源表）
        |
        v
merge_sources()         依（日期, 股票代號）合併成寬表，去重、轉數值型態
        |
        v
build_day_trade_label()  計算「是否為當沖股」label
add_derived_flags()       加上高振幅 / 高成交量變動 / 高當沖比率旗標
        |
        v
LaggedFeatureBuilder      依股票分組，建立 n=3 天的滯後特徵
                          （只保留有足夠歷史資料的股票，避免新股全 NaN）
        |
        v
time_based_split()       依日期切分 train / validation（絕不 random split，
                          避免用未來資料驗證過去模型）
        |
        v
DayTradeModel (LightGBM)  scale_pos_weight 處理類別不平衡 -> 訓練 -> 評估
```

對應到程式檔案：

| 檔案 | 職責 |
|---|---|
| `src/data_interface.py` | 資料來源抽象介面 + Mock 實作 |
| `src/labeling.py` | Label 計算、多表合併、業務規則旗標 |
| `src/feature_engineering.py` | 滯後特徵建構（fit/transform 分離） |
| `src/model.py` | LightGBM 訓練 / 預測 / 評估 |
| `src/pipeline.py` | 串起以上所有步驟 |
| `train.py` | CLI 進入點 |
| `tests/test_labeling.py` | Label 業務規則的單元測試 |

## 三、工程設計決策（重構時做的取捨）

### 1. 為什麼要抽出 `MarketDataSource` 介面？
原始 notebook 把「呼叫內部系統 API」和「特徵工程/建模」寫在同一個 cell 裡，
直接耦合了公司內部的私有 SDK 與連線資訊，沒辦法公開分享，也沒辦法在沒有
內網權限的環境下測試程式邏輯本身對不對。拆出抽象介面後，`pipeline.py`
完全不知道背後接的是內部系統還是假資料，這是標準的 Adapter Pattern，
換資料源、寫測試、公開分享程式碼，三個問題一次解決。

### 2. 為什麼一定要按時間切分 train/validation？
金融時間序列資料如果用 `train_test_split(random_state=...)` 隨機切分，
驗證集裡混入了訓練集「未來」的資料，模型等於偷看到未來才驗證，
績效數字會嚴重虛高。`time_based_split()` 保證驗證集永遠是訓練集之後的日期。

### 3. 滯後特徵為什麼要用前向填充而不是補平均值？
`LaggedFeatureBuilder` 建立滯後特徵後只用 `ffill()`，不用整體平均/中位數補值。
用平均值填補會把「未來才算得出來的統計量」洩漏進當下的特徵裡（data leakage）；
前向填充只使用該股票「當下已經發生」的資訊，符合實際交易時「只能用當下已知資料」
的限制。

### 4. 修正了原始版本一個容易忽略的 bug
原始 notebook 的 `evaluate()` 對「已經在 `train()` 階段做過一次滯後特徵處理」
的驗證集，又呼叫了一次 `create_lagged_features()`，等於對已經位移過的資料
再位移一次。這份重構版本把「訓練時順便處理好的驗證集」與「對全新原始資料做推論」
兩種情境分開（`evaluate()` 吃已處理資料、`predict()` 才會重新跑特徵工程），
避免這種隱蔽的重複位移問題。

### 5. 類別不平衡：選 `scale_pos_weight`，不選 SMOTE
正樣本比例約 25-32%（依日期而定），中度不平衡。這裡選擇 LightGBM 內建的
`scale_pos_weight` 而非 SMOTE 類的過採樣，是因為正樣本比例本身有明確的業務意義
（「當沖比例前 30 名」的定義），過採樣合成的樣本可能扭曲這個分布，
用權重調整比較符合這個情境。

## 四、原始版本的實測結果（僅供參考）

Mock 資料，無法重現這些數字**——這裡列出來是為了說明模型在真實資料上
確實有效，重構本身沒有改變模型邏輯：

|---|---|
| 準確率 | 0.9034 |
| 精確率 | 0.8107 |
| 召回率 | 0.8835 |
| F1 分數 | 0.8455 |
| AUC-ROC | 0.9622 |
| 平均每日命中率 | 0.8822 |

混淆矩陣（驗證集，共 3,385 筆）：TP 895 / FP 209 / TN 2,163 / FN 118

特徵重要性前幾名（來自原始實驗）：`當沖比例_lag1`、`週轉率(%)_lag1`、
`相對強弱比(日)_lag1`——當沖比例與週轉率的近一日表現是最重要的預測訊號，
符合「當沖熱度有短期延續性」的市場直覺。

## 五、如何執行

```bash
pip install -r requirements.txt
python train.py --start-date 2024-01-01 --end-date 2024-06-30
pytest tests/
```

預設使用 `MockMarketDataSource` 產生示範資料；要接上真實資料來源，
只需要實作一個新的 `MarketDataSource` 子類別（可參考 `data_interface.py`
檔案最下方的示意程式碼），並在 `train.py` 換掉 `MockMarketDataSource()` 即可，
其餘 pipeline 完全不用修改。

## 六、已知限制與後續方向

- 目前是單一時間窗口的 train/validation 切分，尚未做 walk-forward
  cross-validation，模型穩定性只在單一驗證窗口驗證過。
- 特徵重要性顯示模型高度依賴 `_lag1` 特徵，代表市場狀態變化快時
  模型可能需要更頻繁重新訓練；尚未量化「多久要重新訓練一次」。
- 目前沒有交易成本、滑價、實際可執行性（流動性衝擊）的模擬，
  預測準確率高不直接等於策略可以獲利，這是模型評估與策略回測
  之間常見的落差，後續應該加上簡易回測層驗證。
